# v0.1 — Consolidated release-candidate acceptance

**Decision:** target a **local-first, foreground-only developer preview** before continuing optional operating-system service installation. This is a deliberate narrower delivery profile, **not** a declaration that Milestone 18D's complete Windows SCM/systemd release gates have passed.

## Supported v0.1 scope

- Private pinned npm tarball installed to an operator-controlled user prefix. No npm registry publication or administrator privileges.
- Installed `cline-orchestrator` CLI: config, diagnose, read-only setup plan, explicit confirmed project/workspace setup, foreground daemon, supervised task commands and events.
- An explicitly started **read-only** localhost dashboard and offline setup HTML snapshot. No browser-mediated task approvals, direct Cline execution buttons, remote dashboard, or generic machine control.
- Existing authenticated local Cline integration and Safety/workspace/validation gates, with per-action confirmation retained. No service auto-installation/start, deployment, remote listener or new release authority.
- Local OpenAI-compatible provider such as `llama.cpp` through its own reviewed model alias and loopback `/v1` endpoint. Provider compatibility and successful **real** task execution require live operator acceptance; a passing config/parser test cannot demonstrate model performance.

**Deferred from the v0.1 foreground distribution:** Windows SCM service packaging/signing, Linux persistent systemd installer, automatic daemon startup/recovery, full installed-service conflict/rollback matrix, comprehensive graphical operator actions, external remote control, multi-browser WCAG certification, signed installer and public production claims. The M18D full-service acceptance gap remains open for a future service-enabled release; do not silently mark it complete. M18F staged distribution still needs an explicit candidate-specific decision.

## Acceptance gates — one candidate, one evidence packet

| Gate | Automated evidence | Operator acceptance / outcome |
|---|---|---|
| A. Pinned distribution | CI build, allowlist, installed Windows/Ubuntu package, uninstall/owned-data sentinels | Record exact Git SHA, Node/npm, archive SHA-256, selected target platform |
| B. First-run experience | **Actual installed JS** `--config`, `diagnose`, `setup`, `status`, create-only `setup-view`, nonreplace, no implicit registry/service writes | On clean Windows user prefix complete first-run steps and check messages are understandable |
| C. llama.cpp compatibility | Config schema and loopback restrictions; CI does **not** contact model | Real `GET http://127.0.0.1:8080/v1/models` returns the configured model ID; one bounded real Cline task executes |
| D. Workspace/Safety | Existing registration, authority and diff-safety tests | Register a disposable Git repository/project and explicit Safety profile; reject any out-of-scope edit |
| E. Task lifecycle | Existing orchestration/task, checkpoint/recovery regressions | Record task ID, event history, reviewed diff, test result, abort/restart/recovery outcomes |
| F. Operator dashboard | Installed localhost HTTP and Chrome acceptance, zero authority, strict CSP, mobile/desktop smoke | Human checks real task/history readability, unknown/missing feeds remain **Unknown**, and browser cannot mutate tasks |
| G. Removal/support | Windows/Ubuntu npm removal and external file digests | Stop foreground processes, uninstall only product files and preserve operator-owned configuration and history |
| H. Release decision | All checks green on one exact candidate | Human signoff for **foreground-only preview**; separate tag, publication or deploy authority if later requested |

Do **not** infer passing Gates C, D, E or human F from synthetic CI fixtures. If the actual model, task and UI do not work together, v0.1 is **not accepted**.

## Windows operator pilot (manual; no automated mutations of the user's workstation)

Only proceed from a **clean or disposable working directory**; inspect `git status --short --branch`, registrations, running listeners and existing installs first. Never overwrite an existing config, registry, workspace or service to make the pilot pass.

1. Build/choose a reviewed `cline-orchestrator-0.1.0.tgz`, record SHA-256, install it under a **new** user-owned prefix using Node.js >=22.15. On Windows, npm creates `cline-orchestrator.cmd` at the prefix root. On Linux the shim is under `<prefix>/bin`.
2. Independently verify the already running `llama.cpp` server's `/v1/models` output, active model alias and response to one harmless test prompt. `8080` is an **example**; use the user's actual loopback port. Do not launch a new model/server or change GPU flags as part of CI.
3. Create a new JSON config draft with no raw secret values:

```json
{
  "schemaVersion": 1,
  "provider": {
    "providerId": "ollama-openai",
    "modelId": "qwen38-27b-192k",
    "baseUrl": "http://127.0.0.1:8080/v1"
  },
  "runtime": {
    "autoApproveCommands": false,
    "autoApproveEdits": false
  },
  "daemon": { "host": "127.0.0.1", "port": 4317 }
}
```

The model ID must **exactly match** what the server advertises; this is an illustrative alias, not a guaranteed match. The CLI's provider readiness preflight may report `Unknown` for this compatibility path; verify functionality separately and do not turn an unproven provider status into `Ready`.

4. From the **installed binary**, run `--config <config.json> config`, `--config <config.json> diagnose <workspace>` and `setup <workspace>`. Use only disposable **existing** workspace paths, record the read-only plan, and optionally create an offline `setup-view` HTML page in a new target file.
5. With interactive confirmations, run `setup-project` then `setup-workspace` using a reviewed bounded Safety profile (allowed paths, protected paths, max files, validation command, worker profile). Confirm only the reviewed registration; do not register an arbitrary filesystem root. Record actual IDs from receipts.
6. Start the daemon only through the reviewed foreground/confirmed `setup-start <workspace-id>` path, after model preflight. In a separate terminal, set a new strong local `ORCH_VIEWER_TOKEN` (never put it in a URL, file or issue) and start `viewer`. Open `http://127.0.0.1:4321/viewer` manually if the configured viewer port is 4321.
7. With an explicitly registered safe test repository, request a small legitimate Cline task such as *add one focused test under src and run its validation*. Verify human approval/denial behavior, workspace isolation, events, diff safety and resulting test. Inspect task history in the dashboard. Do not use a production or sensitive repository for the pilot.
8. Check a safe abort/recovery scenario with real task evidence and no hidden automatic restart. Stop both foreground processes; prove their loopback ports release. Uninstall the temporary npm package, compare hashes of the four user-owned data categories and record any residual files. No `sc.exe` or `systemctl` operation is part of this pilot.

## Capture and release decision

Record one candidate's commit + tarball SHA-256 + installed module identity, source CI run URLs, Windows pilot OS/Node version, Cline/provider model alias/endpoint class (not secrets), sanitized task IDs and validation outcomes, screenshot/evidence of viewer behavior, failure/recovery results, and exact uninstall preservation. Record each gate as **pass, fail, deferred (excluded from v0.1), or not run**, with a named human reviewer. A deferred required foreground gate is a **no-go**. Never publish raw tokens, local paths or task contents in public CI artifacts.

**Status at plan creation:** automated integration expansion is pending CI, and the Windows real-model end-to-end pilot has **not** been executed. M18F release/tag/distribution is **not authorized** by this plan.
